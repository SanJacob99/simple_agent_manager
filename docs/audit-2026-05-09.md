# Codebase audit — 2026-05-09

<!-- last-verified: 2026-05-09 -->

A full-codebase audit identifying schema surfaces that are ahead of runtime
wiring, scaffolded code paths that never execute, and proposals for features
to add or finish. Companion to [`README.md`](../README.md),
[`design.md`](../design.md), and [`AGENTS.md`](../AGENTS.md).

The audit was conducted against branch `claude/audit-codebase-LkcoS` at the
date above. Every gap below is grounded in a file path. A handful of items
are deliberately deferred per `design.md §6`; those are noted inline so they
are not mistaken for accidental omissions.

---

## 1. Executive summary

Simple Agent Manager is structurally complete on the **core path**: graph
editor → resolved `AgentConfig` → run-coordinator → streamed reply.
OpenRouter chat, tool execution, transcript persistence, sessions, sub-agents,
agent-to-agent comms, and cron scheduling all work end-to-end. Where the
project drifts is in **breadth**: several first-class node types
(`mcp`, `vectorDatabase`, `connectors`) ship a schema, a UI editor, and a
concept doc, but no runtime ever consumes their config. Several hook
lifecycle events are typed but never fired. Provider support is single-vendor
(OpenRouter) despite a plugin SDK designed for many.

The cleanest framing is: **the editor and the schema are ahead of the
runtime**. Closing that gap — and extending the runtime in the directions
the schema already advertises — is the bulk of the work below.

### Top-priority gaps (ordered by impact)

1. **MCP client runtime** — schema, UI, and docs ship; no client exists.
2. **Vector database / RAG runtime** — schema, UI, and docs ship; no embedding
   or retrieval code exists.
3. **Connectors runtime** — schema and UI ship; no loader, no tools generated.
4. **Multi-provider plugin coverage** — only OpenRouter is registered, even
   though `ProviderPluginRegistry` and `plugin-sdk` are built for many.
5. **Hook execution coverage** — 12 of 18 declared hook events are dead code.
6. **Storage maintenance** — retention/rotation/pruning fields are read by
   nothing.
7. **Memory persistence and semantic search** — `MemoryEngine` is in-memory
   only despite `MemoryBackend: 'external' | 'cloud'` in config.
8. **Cron in the sidebar palette** — node, editor, and scheduler all exist;
   only the drag-source is missing.

## 2. Schema-only / stubbed runtime surfaces

These are config surfaces that the resolver builds, the UI exposes, and the
runtime never reads. Each one is a "follow-through" task — the schema is the
hard part; the missing piece is execution.

### 2.1 MCP (Model Context Protocol)

- **Schema:** `shared/agent-config.ts` `ResolvedMcpConfig` (transport,
  command, args, env, headers, toolPrefix, allowedTools, autoConnect).
- **UI:** `src/nodes/MCPNode.tsx`, `src/panels/property-editors/MCPProperties.tsx`
  with an `unknown: 'Not yet connected'` status (`MCPNode.tsx:23`,
  `MCPProperties.tsx:23`).
- **Protocol event:** `mcp:status` in `shared/protocol.ts`; status updates
  tracked by `src/store/agent-connection-store.ts`.
- **Manifest entry:** `docs/concepts/_manifest.json` lists `mcp.runtime: null`.
- **Concept doc:** `docs/concepts/mcp-node.md` exists.
- **What's missing:** no MCP client in `server/`. No stdio / SSE / streamable-HTTP
  transport. `config.mcps` is never read by `agent-runtime.ts`. No tool
  catalog ingestion, no autoConnect logic, no allowedTools filtering at
  invocation time.
- **Proposal:** add `server/mcp/mcp-client.ts` with a transport multiplexer
  (`stdio`, `http`, `sse`); load tools at agent start, prefix them per
  `toolPrefix`, surface `mcp:status` from the connection state machine,
  filter against `allowedTools` in the tool factory.

### 2.2 Vector database / RAG

- **Schema:** `ResolvedVectorDatabaseConfig` (label, provider, collectionName,
  connectionString) at `shared/agent-config.ts:378`.
- **UI:** `src/nodes/VectorDatabaseNode.tsx`,
  `src/panels/property-editors/VectorDatabaseProperties.tsx` (4 fields).
- **Manifest entry:** `runtime: null`.
- **Concept doc:** `docs/concepts/vector-database-node.md` exists; reads as
  aspirational.
- **What's missing:** no embedding pipeline, no retrieval tool, no integration
  with `MemoryEngine` or system-prompt assembly. Always cleared in
  sub-agents (`sub-agent-executor.ts:115` sets `vectorDatabases: []`).
- **Proposal:** add `server/runtime/vector-store.ts` with adapter interfaces
  for at least one backend (e.g. Qdrant or local SQLite-vector), expose a
  built-in `vector_search` tool gated on a connected `vectorDatabase` node,
  and optionally a `memory_recall_semantic` variant of the existing memory
  tool.

### 2.3 Connectors

- **Schema:** `ResolvedConnectorConfig` (label, connectorType, config) at
  `shared/agent-config.ts:335`.
- **UI:** `src/nodes/ConnectorsNode.tsx`,
  `src/panels/property-editors/ConnectorsProperties.tsx` (label + dynamic
  config map).
- **Manifest entry:** `runtime: null`.
- **What's missing:** no connector loader, no tool generation, no execution.
  Always cleared in sub-agents (`sub-agent-executor.ts:112`).
- **Proposal:** decide first whether "connectors" stays a separate concept or
  collapses into MCP/plugins. If it stays, define a connector SDK that maps
  a `connectorType` to a tool bundle (e.g. `slack`, `github`, `notion`),
  with an OAuth-or-token auth shape and per-connector tool prefixes.

### 2.4 External memory backends

- **Schema:** `MemoryBackend: 'builtin' | 'external' | 'cloud'`,
  `externalEndpoint`, `externalApiKey` in
  `shared/agent-config.ts` and `MemoryNodeData`.
- **Runtime:** `server/runtime/memory-engine.ts` is in-memory only with
  keyword search.
- **UI:** `MemoryProperties.tsx` only exposes `builtin` / `cloud` — `external`
  is not selectable in the dropdown despite being in the schema.
- **Proposal:** either remove the `external` variant or implement a thin HTTP
  adapter that talks to `externalEndpoint` for `save` / `search` / `recall`
  with `externalApiKey` as Bearer auth. If kept, expose `external` in the UI
  picker so a user can actually select it.

### 2.5 Storage maintenance

- **Schema:** `ResolvedStorageConfig` includes retention, max disk bytes,
  daily reset / rotation flags. `StorageProperties.tsx:221` exposes
  `Max Disk (bytes, 0=disabled)`.
- **Runtime:** `StorageEngine` does not implement any of those fields. There
  is a `MaintenanceScheduler` in `server/scheduling/`, but the storage
  engine itself does not honor retention or daily-reset settings.
- **Proposal:** wire `MaintenanceScheduler` to `StorageEngine.runMaintenance()`
  on a configurable cadence; have `StorageEngine` enforce
  `maxDiskBytes`, retain N most-recent transcripts, and rotate or
  daily-reset memory files when those flags are set.

### 2.6 Multi-provider plugin coverage

- `server/providers/plugins/index.ts` registers exactly one plugin
  (`openrouter`).
- `shared/plugin-sdk` defines `ProviderPluginDefinition` with auth methods,
  catalog, web-search, and web-fetch hooks — all designed for many providers.
- README explicitly notes other providers use static curated model lists in
  the UI, with no live discovery and no auth validation.
- **Proposal:** ship at least Anthropic, OpenAI, and Google providers as
  `ProviderPluginDefinition`s. Each contributes catalog discovery + auth
  validation. The chat path can stay on `pi-ai`, but discovery and key tests
  must light up. This unblocks the existing `Provider` and `Defaults` UI.

## 3. Hook system — 12 of 18 hooks are dead code

`server/hooks/hook-types.ts` declares 18 hook events. `hook-registry.ts` is a
real waterfall registry. Only the following are actually invoked:

| Hook | Invocation site |
| --- | --- |
| `MESSAGE_RECEIVED` | `run-coordinator.ts:318` |
| `SESSION_START` | `run-coordinator.ts:958` |
| `BEFORE_MODEL_RESOLVE` | `run-coordinator.ts:1134, 1592` |
| `BEFORE_PROMPT_BUILD` | `run-coordinator.ts:1150, 1612` |
| `BEFORE_AGENT_REPLY` | `run-coordinator.ts:1189, 1646` |
| `AGENT_END` | `run-coordinator.ts:2444` |
| `AGENT_BOOTSTRAP` | internal, fired in system-prompt assembly |

Declared but never invoked anywhere:

`BEFORE_TOOL_CALL`, `AFTER_TOOL_CALL`, `TOOL_RESULT_PERSIST`,
`BEFORE_COMPACTION`, `AFTER_COMPACTION`, `BEFORE_INSTALL`, `MESSAGE_SENDING`,
`MESSAGE_SENT`, `SESSION_END`, `BACKEND_START`, `BACKEND_STOP`.

`hook-types.ts:97` even labels the section "Scaffolded hook contexts (types
defined, integration deferred)". That comment is honest, but the cost is
that plugin authors have no way to observe tool calls, compaction, or
session end — exactly the events most plugins want to hook.

**Proposal:** wire these in priority order:

1. `BEFORE_TOOL_CALL` / `AFTER_TOOL_CALL` — at the tool-adapter boundary in
   `server/tools/tool-adapter.ts`. Highest leverage; enables auditing,
   redaction, denylists, and rate limiting plugins.
2. `BEFORE_COMPACTION` / `AFTER_COMPACTION` — at the call site in
   `context-engine.ts`. Lets plugins capture summaries.
3. `MESSAGE_SENDING` / `MESSAGE_SENT` — at the WS broadcast point.
4. `SESSION_END` — at session close in `session-router.ts`.
5. `BACKEND_START` / `BACKEND_STOP` — in `server/index.ts` and the shutdown path.
6. `TOOL_RESULT_PERSIST` and `BEFORE_INSTALL` — once `BEFORE_TOOL_CALL` has
   set the precedent.

## 4. Provider gaps and limitations

- **Single registered plugin.** `PLUGIN_MAP` in
  `server/providers/plugins/index.ts` has one entry. The plugin registry,
  loader, auth scaffolding, and catalog cache exist but have no plugins to
  load.
- **No live key validation** for any provider except OpenRouter.
- **No catalog discovery** for Anthropic, OpenAI, Google, xAI — all UI lists
  are hand-curated.
- **Custom model picker** (`e2e/custom-model.spec.ts` covers this) lets
  users paste a model id, but no provider plugin offers capability detection
  for the typed value.

## 5. UI gaps

### 5.1 Cron is not in the sidebar palette

- Registered in `src/nodes/node-registry.ts`.
- Editor: `src/panels/property-editors/CronProperties.tsx`.
- Runtime: `server/scheduling/cron-scheduler.ts` is fully working with tests.
- **Missing:** entry in `PERIPHERAL_ITEMS` in `src/panels/Sidebar.tsx`
  (around line 60–73). The README also says "treat `cron` as in-progress
  unless you verify the full execution path." It's verified — promote it.
- **Doc consequence:** add `docs/concepts/cron-node.md` and add the entry to
  `docs/concepts/_manifest.json`. `AGENTS.md` already calls this out as a
  known follow-up.

### 5.2 Chat drawer features

- **Implemented:** message delete (`MessageBubble.tsx:417-425`),
  abort/cancel (`ChatDrawer.tsx:306`), reasoning collapse, transcript load.
- **Missing:** edit a user message and re-run, regenerate the last assistant
  reply, retry on error, fork-from-message (transcript-store does branching
  internally — the UI never exposes it).
- **Proposal:** start with `regenerate` and `edit-and-resend` since the
  transcript store already supports branch trees.

### 5.3 Schema fields with no editor

- `MemoryNodeData.externalEndpoint` / `externalApiKey` — schema defined,
  not in the dropdown options for `MemoryProperties.tsx`.
- `ToolsNodeData.maxSubAgents` — defined in the schema, no number control
  in `ToolsProperties.tsx`.
- `AgentNodeData.systemPromptMode` — referenced in defaults; not exposed on
  the per-agent property panel.

### 5.4 SubAgent recursion (intentional)

- `SubAgentProperties.tsx:340`: "Off by default. Recursion is disabled until
  product is ready." This is deliberate — leave it off until the depth /
  budget guards mirror the agent-comm safety controls.

### 5.5 Memory backend dropdown has no `external` option

See §2.4. Either drop the schema variant or expose it.

## 7. Documentation gaps

- **Concept docs describe runtimes that don't exist** for `mcp`,
  `vectorDatabase`, and `connectors`. They should either flag the runtime as
  "planned" explicitly or be deferred until §2 lands.
- **Cron concept doc is missing.** The schema includes `cron`; the manifest
  does not. `AGENTS.md` and `CLAUDE.md` both note this.
- **`docs/concepts/_manifest.json`** has `runtime: null` for `skills`,
  `connectors`, `vectorDatabase`, and `mcp`. `skills` is intentional (folded
  into the prompt). The other three are not.
- **`shared/user-tool-manifest.ts` has 7 explicit `// TODO:` schema slots:**
  `description`, `author`, `license`, `homepage`, `sha` (commit pin for
  reproducibility), `installedAt`, `samVersion`. The user-plugins-design doc
  references these explicitly.

## 8. Smaller follow-ups discovered during the audit

- **Proactive compaction trigger.** `ContextEngine.afterTurn()` exists but is
  not invoked from the run loop. Without it, compaction is reactive only.
- **MemoryEngine has no semantic search.** Keyword match against an in-memory
  list. Even a cosine-similarity backend over embeddings stored in
  `vectorDatabases` would be an unlock.
- **Run-coordinator file size.** `server/agents/run-coordinator.ts` is
  2,755 lines. Not a bug, but it's earned a refactor pass — splitting
  channel-comm dispatch, sub-agent dispatch, and main run dispatch into
  separate modules with the coordinator as the thin orchestrator would make
  hook-wiring (§3) safer.
- **Subagent inheritance.** `sub-agent-executor.ts` clears `connectors`,
  `vectorDatabases`, and `crons` for the child. Once those runtimes exist,
  decide per-feature whether the child inherits or starts blank.
- **No webhook ingress for agent triggers.** `server/connections/webhook-handler.ts`
  exists; verify what it triggers and whether it's reachable from the UI.
  An event-triggered agent (alongside time-triggered cron) is a natural
  extension.

## 9. New feature proposals (beyond closing schema gaps)

These are forward-looking. Read against `design.md §6` first — anything that
contradicts an intentional absence belongs in a design discussion, not a
direct PR.

### 9.1 Compatible with current design

- **Cost / token budget alerts.** `payload-breakdown.ts` already produces the
  data; surface daily and per-session spend in the chat drawer with a
  configurable warn / block threshold per agent.
- **Run replay / observability.** Transcript JSONL already records the run
  end-to-end. Add a "replay this run with a different model" affordance and
  a structured trace viewer in the chat drawer.
- **Tool result streaming.** Long-running tools (browser, exec, image gen)
  could stream partial output through the existing WS protocol. Today they
  return a single payload at completion.
- **Provider key tester button.** Per-provider, ping the live catalog
  endpoint with the saved key and surface success/failure inline. Today
  only OpenRouter does this.
- **Bundled skill / tool marketplace inside settings.** The plugin loader,
  user-tool-manifest, and `sam install tool` already form a workable spine;
  a one-screen settings tab to browse / install / enable bundled and curated
  community tools would complete the loop.
- **Voice input** to complement the existing TTS tools — STT against the
  same provider plumbing; useful enough for hands-free agent operation.
- **Better guardrails.** Today: `max_input_chars`, `blocked_term`,
  `pii_email`, `pii_ssn`, `pii_credit_card`. Add prompt-injection heuristics,
  output-toxicity / safety classifier hooks, and per-tool denylists driven
  through `BEFORE_TOOL_CALL` (§3). Make the rule set extensible by plugin.
- **Memory pin / forget tools.** First-class write/delete for long-term
  memory entries from the chat surface.
- **Session search.** Full-text across transcripts in the storage tier.
- **Webhook-triggered agents** (already half-present via
  `webhook-handler.ts`) — exposed as a node type alongside `cron`.

### 9.2 Worth considering, but check `design.md` first

- **Cross-graph node library.** Explicitly absent today (`design.md §6`).
  If product wants reusable subgraphs, the design doc has to move first.
- **Collaborative editing.** Currently single-user; the storage layer is
  filesystem-only. Multi-user is a non-trivial scope shift.
- **Server-rendered graph state.** The canvas is client-authoritative by
  design. Don't move it without revisiting `design.md §5`.

## 10. Suggested sequencing

A short-to-long ordering that minimizes rework:

1. **Tighten what already works.** Add cron to the sidebar (§5.1), expose
   `external` in the memory dropdown or remove the schema (§2.4), expose
   `systemPromptMode` and `maxSubAgents` in the editors (§5.3), add
   `docs/concepts/cron-node.md` (§7).
2. **Wire the missing hooks** — `BEFORE_TOOL_CALL`, `AFTER_TOOL_CALL`,
   compaction, message lifecycle, session end (§3). This unlocks plugin
   authors and is a prerequisite for several proposals in §9.
3. **Add multi-provider plugins** — at least Anthropic, OpenAI, Google
   (§4). Catalog and key validation only — keep chat on `pi-ai`.
4. **Build the MCP client** (§2.1). Largest individual feature; high user
   value.
5. **Build vector / RAG runtime** (§2.2). Naturally extends MemoryEngine.
6. **Decide connectors' fate** (§2.3) — implement or deprecate.
7. **Storage maintenance + memory persistence** (§2.5, §2.4). Makes long-
   running deployments honest about disk usage.
8. **Forward-looking features** from §9.1 once the schema-runtime gap is
   closed.
